Looking at the actual state of the project, I would **not** start building ML yet.

# What I Would Do Next

## Phase 1: Finish Data Integrity

Before ML.

### Priority 1

Link every bet leg to fixture_id

Right now this is the most important task.

You cannot properly engineer features until every leg is tied to:

* Sport
* Tournament
* Fixture
* Market
* Outcome

Structure should become:

```
Bet Leg

↓

Fixture

↓

Tournament

↓

Sport

↓

Market

↓

Outcome
```

Without this, feature generation becomes messy.

---

### Priority 2

Build outcome resolution verification

You currently trust Stake statuses.

Create a validation layer.

Example:

```
Arsenal vs Chelsea

Winner

Arsenal
```

Verify:

* fixture exists
* outcome exists
* market exists
* settlement matches

This prevents corrupted training data later.

---

### Priority 3

Build data quality dashboards

Before ML.

You need visibility.

Examples:

```
Fixtures synced
Markets synced
Outcomes synced
Odds snapshots synced
Bet legs synced
Unlinked legs
Missing fixtures
Missing markets
```

This catches ingestion issues immediately.

## Create Historical Snapshot Logic

This is critical.

Never use future information.

Example:

Bad:

```
Arsenal vs Chelsea
Jan 10

Use season stats from March
```

Data leakage.

Model becomes fake.

---

Correct:

```
Arsenal vs Chelsea
Jan 10

Only use data available before Jan 10
```

Every feature must be generated historically.

This is one of the biggest reasons sports models fail.

# Phase 4: Create Feature Generation System

This is the next major milestone.

Create something like:

```
backend/
├── ml/
│   ├── feature_generation/
│   │   ├── winner_features.py
│   │   ├── totals_features.py
│   │   ├── handicap_features.py
│   │   └── common_features.py
```

Notice something important:

Separate models by market.

---

I would NEVER train:

```
Winner
Totals
Handicap
BTTS
```

inside the same model.

---

Instead:

```
Winner Model

Totals Model

Handicap Model

BTTS Model
```

Each market behaves differently.

Each requires different features.

# Phase 6: Build Evaluation System

This is where most betting projects fail.

Do NOT evaluate using accuracy.

Example:

```
1.10 favorite

Wins
```

Accuracy says model is good.

Profit says nothing.

---

Track:

* ROI
* Yield
* CLV
* Log Loss
* Brier Score
* Calibration

These matter.

# Very Important Change I Would Make

You currently have:

```
bet_history
bet_legs
```

I would add:

```
feature_snapshots
```

Table.

Example:

```
feature_snapshots

id

fixture_id

snapshot_time

feature_json
```

This lets you preserve exactly what the model saw at prediction time.

Without this, retraining and debugging later becomes extremely difficult.
